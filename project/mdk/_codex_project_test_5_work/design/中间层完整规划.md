**数据传递原则**：
- 协议层是生产者，中间层是消费者，通过查询接口解耦
- 协议层不主动推数据给中间层，中间层每 5ms 主动拉
- 算法层输出 action_t[] 给中间层（值拷贝，一次 load）
- 中间层只输出速度指令给控制层，不反向修改算法层/协议层状态

## 三、视觉层 (OpenART Plus) 协议定义

### 3.1 包类型 0x01 — 全图包 (FULL_MAP)

用途：MCU 主动请求时发送（开局 + 重规划触发 + 偶尔矫正）。OpenART 不自主决定发包时机，等 MCU 发请求包（0x03）后回复。收到后触发 solve() 重新规划。

| 偏移 | 字段 | 字节 | 说明 |
|------|------|------|------|
| 0 | 包头 | 2 | 0xA5 0x5A |
| 2 | 类型 | 1 | 0x01 = FULL_MAP |
| 3 | 地图宽度 | 1 | 16 |
| 4 | 地图高度 | 1 | 12 |
| 5 | 墙体位图 | 24 | 192 bits = 16×12, 1=墙 |
| 29 | 箱子数量 | 1 | 0-4 |
| 30 | 箱子坐标 | 8 | 4箱 × 2B (grid_x, grid_y) |
| 38 | 目标数量 | 1 | 0-4 |
| 39 | 目标坐标 | 8 | 4目标 × 2B (grid_x, grid_y) |
| 47 | 炸弹数量 | 1 | 0-2 |
| 48 | 炸弹坐标 | 4 | 2炸弹 × 2B (grid_x, grid_y) |
| 52 | 车X坐标 | 2 | mm, int16 |
| 54 | 车Y坐标 | 2 | mm, int16 |
| 56 | 车朝向 | 2 | deg×10, int16 (0.1°分辨率) |
| 58 | 校验和 | 1 | XOR 全部字段 |
| **合计** | | **59** | |

### 3.2 包类型 0x02 — 位置更新包 (POS_UPDATE)

用途：高频持续发送，提供实时车位姿+箱子位置。

| 偏移 | 字段 | 字节 | 说明 |
|------|------|------|------|
| 0 | 包头 | 2 | 0xA5 0x5A |
| 2 | 类型 | 1 | 0x02 = POS_UPDATE |
| 3 | 帧序号 | 1 | 0-255 循环，检测丢帧 |
| 4 | 车X坐标 | 2 | mm, int16 |
| 6 | 车Y坐标 | 2 | mm, int16 |
| 8 | 车朝向 | 2 | deg×10, int16 |
| 10 | 箱子数量 | 1 | 0-4 |
| 11 | 箱子坐标 | N×2 | 每箱 (grid_x, grid_y), -1=-1 表示已完成消失 |
| ~ | 炸弹数量 | 1 | 0-2 |
| ~ | 炸弹坐标 | M×2 | 每炸弹 (grid_x, grid_y) |
| ~ | 校验和 | 1 | XOR 全部字段 |

### 3.3 包类型 0x03 — MCU 请求包 (MAP_REQUEST)

MCU → OpenART，触发 OpenART 回发一次 FULL_MAP 包。

| 偏移 | 字段 | 字节 | 说明 |
|------|------|------|------|
| 0 | 包头 | 2 | 0xA5 0x5A |
| 2 | 类型 | 1 | 0x03 = MAP_REQUEST |
| 3 | 原因 | 1 | 0x01=开局初始化 / 0x02=STUCK重规划 / 0x03=手动校正 |
| 4 | 校验和 | 1 | XOR 全部字段 |
| **合计** | | **5** | |

**MCU 主动请求触发条件**（在 path_follower.c 中判断）：

| 条件 | 原因字段 | 说明 |
|------|----------|------|
| 系统启动后 `vision_full_map_ready()` 超时 3s 仍未收到 | 0x01 | 开局初始化，防止 OpenART 还没发 MCU 就开始等 |
| `g_state == FOLLOWER_STUCK` | 0x02 | 卡住后需要完整地图重规划 |
| 蓝牙命令 `MAP_REQ` | 0x03 | 调试期间手动强制刷新地图 |

> OpenART 收到 0x03 请求后，在下一帧视觉更新时回发一次 FULL_MAP（0x01 包）。
> MCU 发出请求后进入等待，最多等 2s，超时后再次发请求（最多重试 3 次）。

### 3.4 带宽可行性

UART5 @ 115200bps = 14400 字节/秒。
POS_UPDATE ~20 字节/帧 → 可发 720 帧/秒，实际只需 10-30Hz，带宽充裕。
FULL_MAP ~59 字节按需发（MCU 主动请求），完全不影响。
MAP_REQUEST 5 字节偶发，可忽略。
MCU → OpenART 使用同一 UART5 的 TX 线（全双工），DMA 仅用于 RX 收 OpenART 的数据，TX 发请求包用普通 UART 中断或轮询即可（极低频）。

### 3.5 待与视觉组对齐的协议细节

| 序号 | 问题 | 影响 |
|------|------|------|
| 1 | x/y 基准：场地 mm？屏幕像素？网格坐标？ | 决定中间层要不要坐标转换 |
| 2 | θ=0 定义方向 + 旋转方向 | 决定航向控制的正负号 |
| 3 | 箱子 0/1/2/3 编号规则 | 必须和算法层 box_id 一致 |
| 4 | "箱子已完成"表达：坐标发(-1,-1) 还是单独标志位？ | 决定 vision_get_box_grid() 返回值 |
| 5 | 炸弹炸墙后：只标记 walls_changed 还是下发新墙体位图？ | 决定重规划触发条件 |
| 6 | OpenART 收到 MAP_REQUEST(0x03) 后的响应延迟 | 决定 MCU 等待超时阈值 |

## 四、协议层 (vision_parser.c/h) 设计

### 4.1 DMA 环形缓冲方案

```
RT1064 UART5 + DMA:
  · 环形缓冲区大小: 512 bytes (最大包 ~59B × 8 = 足够余量)
  · DMA 写指针: 硬件自动维护
  · 协议层读指针: 软件维护
  · 每 5ms 在 PIT 中断中调用 vision_parser_update()
```

**为什么 DMA 环形缓冲？**
- OpenART 发 10-30Hz，MCU 收 200Hz — 频率不同步
- DMA 自动收，不会丢字节
- 协议层按自己节奏取包，不受 OpenART 发送节奏约束
- 理想情况：发送频率是接收频率的整数倍（如 20Hz : 200Hz = 1:10）

### 4.2 数据结构

```c
// 视觉全局状态（所有动态元素）
```

### 4.4 融合位姿实现

```c
// vision_parser.c 内部静态变量
static int16  g_vis_ref_x, g_vis_ref_y;       // 最近视觉帧的绝对位姿 (mm)
static float  g_vis_ref_theta;                 // 最近视觉帧的朝向 (deg)
static uint8  g_vis_valid;                     // 是否有有效视觉参考

// 每次收到 POS_UPDATE 并校验通过后:
static void vision_on_pos_update(int16 cx, int16 cy, int16 ctheta_x10) {
    g_vis_ref_x = cx;
    g_vis_ref_y = cy;
    g_vis_ref_theta = ctheta_x10 * 0.1f;
    g_vis_valid = 1;
    odometry_reset();  // 以新视觉帧为基准重置里程计增量
}

// 中间层调用的融合位姿
void vision_get_fused_pose(float *x, float *y, float *theta) {
    if(g_vis_valid) {
        *x = g_vis_ref_x + odom_world_x_mm;       // 参考 + 增量
        *y = g_vis_ref_y + odom_world_y_mm;
        *theta = imu963ra_yaw_angle;              // IMU 直接给航向
    } else {
        // 无视觉帧时纯里程计（漂移大，仅调试用）
        *x = odom_world_x_mm;
        *y = odom_world_y_mm;
        *theta = imu963ra_yaw_angle;
    }
}
```

## 五、中间层 (path_follower.c/h) 设计

### 5.1 全部职责清单

| # | 职责 | 说明 |
|---|------|------|
| 1 | Action 队列管理 | load(值拷贝) → 逐条执行 → advance → DONE |
| 2 | 状态机 | IDLE/MOVING/PUSHING(APPROACH+PUSH)/WAITING/DONE/STUCK |
| 3 | 位姿消费 | 调 vision_get_fused_pose() 拿融合位姿 |
| 4 | 箱子消费 | 调 vision_get_box_grid() 拿箱子实时位置 |
| 5 | 位置闭环 P 控制 | P 控制 → 世界速度 vx,vy, KP_POS=5.0 |
| 6 | 航向控制 | theta!=NAN → PD转向, 否则 omega=0 |
| 7 | 到达判定 | 3级阈值: WP_ARRIVE_MM(30)/ARRIVE_MM(25)/PUSH_APPROACH_MM(30) |
| 8 | 推箱两阶段 | APPROACH: P控制走到推箱站位; PUSH_EXEC: 恒定速度推 |
| 9 | PUSH 完成判定 | 视觉闭环: boxes[bid] grid == target; 开环回退: 时间/距离估算 |
| 10 | PUSH 卡住检测 | 箱子位置 1s 不变 → STUCK (阶段三实现) |
| 11 | WAIT 计时 | 倒计时到期 → advance |
| 12 | 超时保护 | 每条 Action 30s 上限 → STUCK |
| 13 | 异常处理 | STUCK → 停车 → 记录原因 → 触发重规划(如有新全图) |
| 14 | 窄通道降速 | 阶段三: narrow_passage 标记 → 速度×50% |
| 15 | 重规划触发 | 收到新全图 or STUCK → 用最新位置调 solve() → 重新 load |

### 5.2 状态机

```
                    ┌─────────┐
          load() ──→│  IDLE   │←── abort()
                    └────┬────┘
                         │ _enter_action()
           ┌─────────────┼─────────────────┐
           ▼             ▼                  ▼
      ┌────────┐   ┌──────────┐      ┌─────────┐
      │ MOVING │   │ PUSHING  │      │ WAITING │
      │        │   │          │      │         │
      │ P控制   │   │├APPROACH │      │ 倒计时  │
      │ 逐wp导航│   ││ P控制   │      │ 到期→   │
      │        │   │├PUSH_EXEC│      │_advance │
      │ 到达→   │   ││ 恒速推  │      └─────────┘
      │_advance│   ││ 视觉判定│
      └───┬────┘   └────┬─────┘
          │             │
          └──────┬──────┘

        ┌──────────────┐   超时 30s

        │ YES → DONE   │
        └──────────────┘
```

### 5.3 各状态逻辑

**MOVING**：
```
每 5ms:
  目标 = waypoints[wp_idx] (有路点) 或 target_x/y 格子中心 (无路点)
  dx = target.x - fused.x
  dy = target.y - fused.y
  dist = sqrt(dx² + dy²)
  
  if dist < 阈值 (WP_ARRIVE or ARRIVE):
      if 还有下个 waypoint → wp_idx++
      else → _advance_action()
  
  vx = clamp(KP_POS * dx, ±MAX_V_MM_S)
  vy = clamp(KP_POS * dy, ±MAX_V_MM_S)
  omega = (theta != NAN) ? _steer_angle(theta) : 0
  motion_set_world_velocity(vx, vy, omega)
```

**PUSHING / APPROACH**：
```
每 5ms:
  目标 = push_meta.car_target 的世界坐标 (grid * 200 + 100)
  dx, dy, dist 同上
  if dist < PUSH_APPROACH_MM → 切到 PUSH_EXEC
  
  vx, vy = P控制 (同MOVING)
  // 复用已有航向保持逻辑，防止平移过程中车体自转偏移导致方向跑偏
  omega = imu963ra_yaw_hold_calculate()
  motion_set_world_velocity(vx, vy, omega)
```

**PUSHING / PUSH_EXEC**：
```
每 5ms:
  // 恒定速度沿推箱方向
  // 注：推箱是虚拟引擎实现，车头方向不影响推箱逻辑，无需对准箱子
  switch(push_meta.push_dir):
      DIR_UP:    vx=0,       vy=-PUSH_V_MM_S
      DIR_DOWN:  vx=0,       vy=+PUSH_V_MM_S
      DIR_LEFT:  vx=-PUSH_V_MM_S, vy=0
      DIR_RIGHT: vx=+PUSH_V_MM_S, vy=0

  // ★ 必须复用 imu963ra_yaw_hold_calculate() 防止推箱过程中车体自转
  //    自转会导致 motion_set_world_velocity 的 vx/vy 方向跑偏，推箱轨迹偏离
  //    auto_control_mode=1 时 IMU 航向保持不自动生效，必须中间层主动给 omega
  omega = imu963ra_yaw_hold_calculate()
  motion_set_world_velocity(vx, vy, omega)

  完成判定（双路径）:
    // ★ 防超推：推到最后一步时提前降速，视觉确认后再停
    if g_push_dist_mm >= (n_steps - 1) * 200:
        将速度减为 PUSH_V_SLOW_MM_S (150mm/s)
    
    // ★ 闭环：箱子在虚拟引擎里到位后消失，vision_get_box_grid() 返回 0(不存在)即完成
    //    不是判定"坐标 == 目标坐标"，而是判定"箱子消失"
    闭环: vision_get_box_grid(box_id) 返回 0 → _advance()
    开环: g_push_dist_mm >= n_steps * 200 + 50 → _advance()  // 多走 50mm 容差再停
    
  // 累计推距（无论哪路判定都更新）
  g_push_dist_mm += current_push_speed * 0.005f  // 降速后用实际速度
```

**WAITING**：
```
每 5ms:
  wait_remaining -= 0.005
  if wait_remaining <= 0 → _advance_action()
  else → motion_set_world_velocity(0, 0, 0)
```

## 十一、关键风险与缓解

| 风险 | 等级 | 缓解 |
|------|------|------|
| 无真实视觉数据时位姿纯靠里程计（漂移大） | 高 | 初版用蓝牙命令注入假位姿测试；后续通过视觉帧间歇性矫正 |
| PUSH 完成判定依赖 OpenART 实时箱子位置 | 高 | 闭环：箱子推到位后虚拟引擎消失，`vision_get_box_grid()` 返回 0 即完成（不是判坐标相等）；无视觉时回退距离估算（末段降速防超推） |
| PUSH_EXEC 阶段车体自转导致 vx/vy 方向跑偏 | 高 | 复用 `imu963ra_yaw_hold_calculate()` 作为 omega，不需要自写 _steer_angle()；推箱是虚拟引擎实现，车头朝向不影响推箱逻辑 |
| 视觉反馈延迟 33-100ms × 750mm/s = 最多超推 75mm | 中 | 最后一步提前降速到 150mm/s；开环回退多走 50mm 容差再停 |
| OpenART 字节级协议未确定 | 中 | vision_parser 留好扩展点，校验和解析框架先搭好 |
| STUCK 后无重规划能力 | 中 | vision_request_full_map(0x02) 触发，path_follower_replan() 接口已留好，阶段三实现 |
| MCU 发请求后 OpenART 无响应 | 低 | 最多重试 3 次，每次等 2s；超时后 STUCK 等人工干预 |
| DMA 环形缓冲溢出（发的太快） | 低 | 512B 缓冲足够存 8 帧全图包；POS_UPDATE 更小 |
| RT1064 内存 (DTCM 128KB) | 低 | 新增模块静态变量 < 2KB，当前编译已通过 |
