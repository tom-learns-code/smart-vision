---- C1. ai_tuner.c:238 — PID参数修改与ISR读取之间的竞态条件 ----
  严重度: 🔴 Critical (运行时数据竞争)

  涉及文件:
    - ai_tuner.c:35-41  (ai_tuner_update_pid)
    - ai_tuner.c:223-239 (ai_tuner_poll_command)
    - blue.c:53-162      (bt_cmd_handler, SYNC_SPEED_PID / SYNC_POS_PID 宏)
    - pid.c:33-64        (position_pid_update)
    - motion_control.c:777-838 (motor_control_5ms, ISR上下文)

  问题描述:
    ai_tuner_poll_command() 在主循环(while(1))中运行, 调用链为:
      main() → ai_tuner_poll_command() → ai_tuner_process_command()
            → ai_tuner_update_pid()         // 修改 motor1_speed_pid.Kp/Ki/Kd
            → reset_pid_state()             // 连续写入6个浮点字段

    同时 PIT ISR (每5ms) 中:
      PIT_IRQHandler() → motor_control_5ms()
                       → 读取 motor0/1/2_speed_pid (Target, Actual)
                       → position_pid_update(&motorX_speed_pid)  // 读写 Error0/1/Int/Out

    ai_tuner_poll_command() 中 interrupt_global_disable() 仅保护了命令缓冲区拷贝
    (ai_tuner_ready_buf → cmd), 未保护实际的PID更新操作。

    同样问题存在于 bt_cmd_handler() 通过 SYNC_SPEED_PID() 宏同时修改三个轮子PID。

  后果:
    - Cortex-M7 单 float 读写是原子的, 但 reset_pid_state() 连续写6个 float
    - ISR 可能在写 PID 参数到一半时触发, 读到: 新 Kp + 旧 Ki (不一致)
    - 最严重情况: ISR 在 reset_pid_state() 写到一半时读取半初始化 PID 结构体,
      导致一个控制周期内使用随机 Error0/ErrorInt/Out 值, 电机失控

  修改建议:
    方案A (最小改动): 在 ai_tuner_update_pid() 和 bt_cmd_handler() 的
    PID修改代码周围添加临界区保护:
      uint32 primask = interrupt_global_disable();
      motor1_speed_pid.Kp = kp;
      motor1_speed_pid.Ki = ki;
      motor1_speed_pid.Kd = kd;
      reset_pid_state(&motor1_speed_pid);
      interrupt_global_enable(primask);

    方案B (更安全): 使用双缓冲PID参数, ISR 在每次控制周期开始时检查并原子地
    交换新旧参数集。避免在 ISR 热路径中使用关中断。

---- C2. path_follower.c:278 — path_follower_load() 15KB memcpy 与 ISR 的数据竞争 ----
  严重度: 🔴 Critical (运行时数据竞争)

  涉及文件:
    - main.c:172-188        (mission_try_start_from_map)
    - path_follower.c:270-288 (path_follower_load)
    - path_follower.c:237-268 (path_follower_update, ISR上下文)
    - isr.c:24-32            (PIT_IRQHandler 调用顺序)

  问题描述:
    main.c mission_try_start_from_map() 中:
      device_init_flag = 1;                           // 阻止电机输出
      path_follower_load(&g_mission_output);          // memcpy 15KB!
      device_init_flag = 0;                           // 允许ISR执行路径

    path_follower_load() 内部:
      memcpy(&g_output, output, sizeof(g_output));    // ~15KB, 可能跨多个5ms周期
      enter_current_action();                          // 设置 g_state

    而 PIT ISR 中 path_follower_update() 在 motor_control_5ms() 之前执行:
      PIT_IRQHandler():
        vision_parser_update();    // ← 正常
        path_follower_update();    // ← 读取 g_output, 可能与主循环 memcpy 冲突!
        motor_control_5ms();       // ← 检查 device_init_flag, 若=1则return

    虽然 device_init_flag=1 保证 motor_control_5ms() 不驱动电机, 但
    path_follower_update() 不检查此标志, 会直接读取 g_output 并修改
    g_state / g_sub_state / g_action_idx 等内部状态。

  后果:
    - memcpy 15KB 在 600MHz 下约需数十微秒, 小于5ms, 现实触发概率较低
    - 但如果其他中断(如CSI camera)抢占, memcpy 可能被推迟, 超过5ms窗口
    - ISR 读到半拷贝的 g_output → 部分 action 有效, 部分为全零
    - g_state 可能被 ISR 改为 FOLLOWER_STUCK, 导致主循环的后续逻辑混乱

  修改建议:
    方案A: 在 path_follower_load() 的 memcpy 周围加临界区:
      uint32 primask = interrupt_global_disable();
      memcpy(&g_output, output, sizeof(g_output));
      g_action_idx = 0;
      enter_current_action();
      interrupt_global_enable(primask);

    方案B: 添加一个 atomic 标志, ISR 中 path_follower_update() 在标志为1时
    跳过执行:
      // main.c
      g_path_loading = 1;
      path_follower_load(&g_mission_output);
      g_path_loading = 0;
      device_init_flag = 0;

      // isr.c path_follower_update() 开头:
      if(g_path_loading) return;

---- H1. blue.c:53 — 蓝牙PID修改可能被PIT ISR抢占 ----
  严重度: 🟠 High

  涉及文件:
    - blue.c:53-162 (bt_cmd_handler, SYNC_SPEED_PID/SYNC_POS_PID 宏)
    - blue.c:32-40 (SYNC_SPEED_PID 宏定义)
    - blue.c:42-50 (SYNC_POS_PID 宏定义)

  问题描述:
    SYNC_SPEED_PID() 宏展开为6次 float 赋值(motor1/2 各 Kp/Ki/Kd)。
    若 bt_cmd_handler() 在 GPIO ISR 中执行(GPIO1_Combined_16_31_IRQHandler
    → wireless_module_spi_handler → bt_cmd_handler), 且 GPIO ISR 优先级
    低于 PIT ISR, PIT ISR 可能在 SYNC_SPEED_PID() 执行到一半时抢占。

    motor2_speed_pid 手工设了不同的 Kp(20 vs 18), SYNC 后会覆盖为与 motor0
    相同。若 ISR 在 SYNC 半途读取, 可能 motor1 用了新值而 motor2 用了旧值。

  修改建议:
    在 bt_cmd_handler() 函数入口和出口加 interrupt_global_disable/enable,
    或确认 GPIO ISR 优先级高于 PIT ISR。

---- H2. vision_parser.c:49 — 环形缓冲区仅留1字节空闲余量 ----
  严重度: 🟠 High

  涉及文件:
    - vision_parser.c:46-54 (vision_parser_rx_handler, ISR上下文)
    - vision_parser.c:316-337 (vision_parser_update, ISR上下文)
    - vision_parser.h:22 (VP_RX_BUF_SIZE = 512U)

  问题描述:
    环形缓冲区写指针检查:
      uint16 next = (uint16)((rx_write_idx + 1U) & (VP_RX_BUF_SIZE - 1U));
      if(next != rx_read_idx) { ... }  // 仅当 next==read 时丢弃, 浪费1字节

    实际可用空间: 511字节 (512 - 1)
    115200波特率下5ms产生: 115200/10/200 ≈ 57.6字节
    vision_parser_update() 每5ms消费: 最多64字节

    正常情况下 64 > 57.6, 刚好够用。但以下场景可能导致溢出:
    - UART 帧间间隔不均匀, 短时突发 > 511字节
    - 更高波特率(如调试时可能改为921600)
    - 未来在 vision_parser_update() 中添加耗时操作, 减少每周期消费量

  修改建议:
    方案A: VP_RX_BUF_SIZE 改为 1024U (必须是2的幂), 留更多余量
    方案B: 在 rx_handler 中添加溢出计数器, 便于运行时诊断

---- H3. solver.c:311 — 静态 map_preprocess_t 包含36KB distances 数组 ----
  严重度: 🟠 High (架构/内存)

  涉及文件:
    - solver.c:311 (static map_preprocess_t pp)
    - solver.c:55-132 (preprocess_init, 对192格全源BFS)
    - solver.h:124-130 (map_preprocess_t 定义, distances[192][192])

  问题描述:
    map_preprocess_t.distances[MAP_CELLS][MAP_CELLS] = 192 * 192 = 36,864字节
    在 DTCM (448KB) 的 BSS 段中。preprocess_init() 对每个非墙格子做全图BFS,
    复杂度 O(V * (V+E)) ≈ O(192 * 192) = O(36,864) 次节点扩展。

    在 600MHz Cortex-M7 上估计耗时 5-15ms (取决于墙密度)。
    该函数在 solve() 中每次被调用, solve() 在主循环中运行。
    如果 solve() 执行超过5ms, PIT ISR 可以抢占——由于 solve 是纯计算
    (不涉及电机控制共享状态), 实际风险较低。但如果有其他中断(CSI camera)
    在 solve 期间大量触发, 可能导致 solve 进一步延迟。

  目前安全, 但需要关注:
    - 192*192 的 uint8 距离意味着最大距离254(255=不可达), 够用
    - 未来若增大 MAP_MAX_W / MAP_MAX_H, 内存呈平方增长

  修改建议:
    暂不修改, 但在地图尺寸增大前需要评估 DTCM 余量。

---- H5. motion_control.c:777 — ISR中大量FPU操作, 需确认FPU上下文保存 ----
  严重度: 🟠 High (配置相关)

  涉及文件:
    - motion_control.c:306-353 (odometry_update: cosf, sinf, atan2f, sqrtf)
    - motion_control.c:406-438 (imu963ra_heading_update: 浮点运算)
    - motion_control.c:504-511 (k_calculate: cosf)
    - isr.c:24-32 (PIT_IRQHandler → motor_control_5ms 调用链)

  问题描述:
    motor_control_5ms() 在 PIT ISR 中执行, 调用链包含大量 FPU 指令
    (cosf, sinf, atan2f, sqrtf)。Cortex-M7 有硬件 FPU (FPv5), 但:
    - FPU 寄存器 (S0-S31) 共32个, 在 ISR 进入/退出时需要保存/恢复
    - 如果 FPU lazy stacking 未正确配置 (SCB->CCR 或 FPCCR),
      ISR 中的 FPU 操作可能破坏主循环的浮点计算上下文

    Keil MDK 默认 startup 通常配置了 lazy stacking, 但需要确认。

  修改建议:
    检查 startup_mimxrt1064.s 中是否包含 FPU 使能代码:
      - SCB->CPACR |= (0xF << 20)  // CP10/CP11 full access
      - FPU->FPCCR  lazy stacking 配置
    若未配置, 添加 FPU 初始化。当前 0 Error 0 Warning 编译通过说明
    至少链接没问题, 但运行时 FPU 状态可能有问题。
