# 全系统分层视觉与中间层协同总体规划

> 文档版本：v1.0  
> 文档日期：2026-06-25  
> 适用范围：OpenART视觉层、UART协议层、RT1064算法层、中间执行层和运动控制层  
> 当前首要目标：先打通一条信息完整、职责明确、能够稳定运行的自动执行链路，再逐步增强系统健壮性

---

## 1. 规划目标

本规划融合以下两份既有设计：

- `中间层完整规划.md`
- `视觉分层识别与事件驱动更新设计.md`

整体实施遵循以下顺序：

```text
先完成可运行闭环
→ 再完善动态对象跟踪
→ 再处理遮挡和爆炸
→ 最后增加异常恢复与协议健壮性
```

当前阶段不追求通用通信框架，也不为低概率故障提前引入大量复杂状态。协议只增加实际运行必需的信息，并通过协议解析层隔离通信细节，避免协议复杂度扩散到算法层和控制层。

## 2. 已确认的比赛规则

### 2.1 地图

- 地图尺寸固定为 `16×12`。
- 第一行、最后一行、第一列、最后一列为不可破坏边界墙。
- 普通墙可以被炸弹破坏。
- 地图格边长为 `200 mm`。

### 2.2 箱子

- 箱子可以被车辆从任意车体朝向推动。
- 箱子不能进入任何墙体。
- 箱子不会推动另一个动态物体。
- 箱子进入不匹配目标点后仍然存在，但可能被目标图层遮挡。

### 2.3 炸弹

- 炸弹可以被车辆从任意车体朝向推动。
- 炸弹不能进入边界墙。
- 炸弹可以进入普通墙并被墙体遮挡。
- 炸弹进入目标点后也可能被目标图层遮挡。
- 炸弹满足爆炸条件后会改变静态墙体地图。

### 2.4 动态物体运动

- 箱子和炸弹每次只沿 X 或 Y 单轴移动。
- 不允许连锁推动。
- 车辆朝向 `car.theta` 不参与判断推动轴和推动方向。
- 推动判断主要使用车辆中心位置、车辆速度、物体速度、相对位置和碰撞规则。

## 3. 全系统分层架构

```text
竞赛系统屏幕
    ↓
OpenART视觉层
    ├─ 静态地图层
    ├─ 动态物体层
    └─ 车辆姿态层
    ↓ UART5
RT1064协议层
    ├─ 数据包解析
    ├─ 视觉状态缓存
    └─ 视觉与里程计位姿融合
    ↓
算法层
    ├─ 消费一致地图快照
    └─ 生成Action序列
    ↓
中间层 path_follower
    ├─ 执行Action
    ├─ 判断推动完成和卡住
    └─ 请求重规划
    ↓
控制层 motion_control
    └─ 世界速度到电机PWM
```

## 4. 状态所有权

每类状态只能有一个主要维护方，避免多层同时推演并相互覆盖。

| 状态 | 主要维护方 | 其他层的权限 |
|---|---|---|
| 墙、地板、目标、地图版本 | OpenART | MCU只读和缓存 |
| 箱子/炸弹ID、位置、可见状态 | OpenART | 中间层读取并核对动作 |
| 车辆视觉位姿 | OpenART | 协议层用于位姿融合 |
| 车辆融合位姿 | MCU协议层 | 中间层读取 |
| Action序列和当前动作 | 算法层/中间层 | 视觉层不修改 |
| 动作完成、停车和重规划 | 中间层 | 视觉层只提供事实状态 |
| 电机速度闭环 | 控制层 | 上层只提供目标速度 |

视觉层可以使用物理规则约束识别，但不能决定当前算法Action是否完成。中间层可以检查视觉结果是否符合预期，但不能直接修改视觉对象位置。

## 5. 全系统统一坐标约定

正式实现前必须在代码和协议中统一以下定义：

```text
地图坐标：
    左上角格为 (0, 0)
    X 向右增加
    Y 向下增加

连续网格坐标：
    一格 = 10个单位
    格中心 (gx, gy) = (gx*10+5, gy*10+5)

世界坐标：
    world_x_mm = grid_x_x10 * 20
    world_y_mm = grid_y_x10 * 20

车辆角度：
    0度方向和正旋转方向必须通过一次实测固定
    协议统一使用 0.1度整数
```

屏幕像素坐标只允许存在于OpenART图像处理内部，不得直接进入算法层或中间层。

## 6. OpenART视觉状态模型

### 6.1 静态地图层

空间精度为一格：

```text
StaticCell {
    class: UNKNOWN | FLOOR | WALL | GOAL
    confidence
    candidate_class
    candidate_count
}
```

保存：

- `static_map_initial`
- `static_map_current`
- `pending_map`
- `map_version`

首帧建立初始地图。后续只有强视觉证据或明确游戏事件可以修改当前地图。

### 6.2 动态物体层

箱子和炸弹使用 `0.1格` 连续坐标：

```text
DynamicObject {
    object_id
    type: BOX | BOMB
    x_x10
    y_x10
    internal_state
    output_state
    locked_axis
    move_direction
    velocity
    visible_fraction
    recent_positions
}
```

内部可以维护较细状态：

```text
FROZEN
ACTIVE
PUSH_CANDIDATE
PUSHING_X
PUSHING_Y
OCCLUDED
SETTLING
BLOCKED
EXPLOSION_PENDING
REMOVED
```

UART首阶段只输出中间层真正需要的简化状态：

```text
VALID       位置有效
OCCLUDED    对象仍存在但被遮挡或依靠短期推算
COMPLETED   已明确完成或因确认事件移除
LOST        状态不可信，不能作为动作完成依据
```

### 6.3 车辆姿态层

```text
CarState {
    front_x
    front_y
    back_x
    back_y
    center_x
    center_y
    theta
    velocity_x
    velocity_y
    confidence
}
```

车辆层独立高频更新，不参与静态建图。

## 7. 第一帧初始化

第一帧允许投入较高计算量：

1. 高质量扫描 `16×12` 网格。
2. 分别建立墙体、地板和目标点静态地图。
3. 识别位于标准格中心的箱子和炸弹。
4. 为动态物体分配稳定 `object_id`。
5. 动态物体所在格的静态底层恢复为地板。
6. 车辆完全排除出一格精度静态建图。
7. 将初始地图和对象表组成同一份一致快照。

首帧对象ID一旦分配，后续不能按照检测顺序重新编号。

---

## 8. 动态物体跟踪

### 8.1 激活与冻结

以车辆连续坐标为圆心：

```text
进入激活半径：1.5格
退出冻结半径：1.8格
```

- 区域内对象进入 `ACTIVE`，执行局部ROI识别。
- 区域外对象进入 `FROZEN`，停止高计算量搜索。
- FROZEN对象仍保留在动态对象表和输出快照中。
- 进入和退出使用连续多帧确认，避免边界抖动。

### 8.2 单轴运动

动态物体开始连续移动后锁定 X 或 Y 轴：

- 锁定X时，Y保持推动前稳定值。
- 锁定Y时，X保持推动前稳定值。
- 不使用车辆朝向推断运动方向。
- 车辆中心速度和相对位置只能作为辅助证据。

### 8.3 碰撞约束

- 箱子进入任何墙体：拒绝该位置更新。
- 炸弹进入边界墙：拒绝该位置更新。
- 炸弹进入普通墙：允许进入遮挡或爆炸候选状态。
- 前方存在另一个动态物体：当前物体不得继续移动。

---

## 9. 遮挡处理

遮挡不等于对象消失。

### 9.1 部分遮挡

- 根据静态地图计算可见部分。
- 使用历史位置和锁定轴限制搜索。
- 可见比例越低，当前视觉位置权重越低。
- 不直接把残片质心当作完整物体中心。

### 9.2 完全遮挡

- 使用最后可靠位置、锁定轴、车辆中心速度和碰撞边界短期推算。
- 车辆停止或推动关系结束后停止外推。
- 对象状态输出为 `OCCLUDED`，不能输出为 `COMPLETED`。
- 只有明确游戏事件才能将对象标记为 `COMPLETED`。

---

## 10. 静态地图更新与爆炸

### 10.1 普通静态校正

- 边界墙永久锁定。
- 动态物体遮挡的格暂停静态更新。
- 低置信度观测不修改已有地图。
- 新类别需要强证据和连续确认。

### 10.2 爆炸事务

爆炸候选出现后：

1. 根据炸弹最后位置和运动轴推导爆炸中心。
2. 从 `static_map_current` 复制出 `pending_map`。
3. 在候选中心周围暂时清除 `3×3` 非边界墙。
4. 对中心周围 `5×5` 区域执行高质量验证。
5. 验证成功后一次性提交地图。
6. `map_version` 增加。
7. 炸弹标记为 `COMPLETED`。
8. 设置 `MAP_CHANGED` 通知MCU。
9. 验证失败则回滚，不发布候选地图。

## 11. 精简通信协议

### 11.1 设计原则

- 继续使用固定包头、固定包类型和XOR校验。
- 首阶段不引入TLV、CRC16和通用事件总线。
- 协议解析细节只存在于OpenART打包模块和MCU `vision_parser`。
- 算法层和中间层只读取解析后的结构体和查询接口。
- 固定对象槽位，避免可变长度解析增加首阶段复杂度。

建议全系统统一上限：

```text
MAX_BOXES  = 4
MAX_GOALS  = 4
MAX_BOMBS  = 3
```

### 11.2 FULL_MAP

MCU发送 `MAP_REQUEST` 后，OpenART返回当前已提交世界状态的一致快照。

逻辑字段：

```text
packet_type
protocol_version
frame_id
map_version
map_width
map_height
wall_bitmap
goal_count + goals
box_count + 固定槽位箱子记录
bomb_count + 固定槽位炸弹记录
car_pose
checksum
```

每个动态对象记录：

```text
object_id
state
x_x10
y_x10
```

`FULL_MAP` 只发送 `static_map_current`，绝不发送尚未提交的 `pending_map`。

### 11.3 POS_UPDATE

高频固定长度位置包：

```text
packet_type
protocol_version
frame_id
map_version
event_flags
car_valid
car_x_mm
car_y_mm
car_theta_x10
固定槽位箱子记录
固定槽位炸弹记录
checksum
```

对象即使处于FROZEN，只要仍然存在，也继续通过固定槽位输出缓存状态。这样本帧未执行视觉搜索不会被中间层误解为对象消失。

首阶段事件标志只保留：

```text
MAP_CHANGED
VISION_DEGRADED
```

### 11.4 MAP_REQUEST

保持MCU主动请求：

```text
STARTUP
STUCK_REPLAN
MAP_CHANGED
MANUAL
```

地图爆炸提交后，OpenART先在 `POS_UPDATE` 中设置 `MAP_CHANGED`。MCU收到后停止依赖旧地图继续执行，并主动请求新的 `FULL_MAP`。

### 11.5 暂不实现的协议能力

以下功能保留为后续增强，不进入首条可运行链路：

- 通用变长TLV协议
- CRC16替换XOR
- OpenART独立重启会话恢复
- MCU向视觉发送完整Action上下文
- 复杂事件确认和重发队列

## 12. MCU协议层

协议层负责将串口包转换为统一内部状态：

```text
vision_world_state
├─ latest_car_pose
├─ boxes[MAX_BOXES]
├─ bombs[MAX_BOMBS]
├─ static_map
├─ map_version
└─ freshness
```

建议查询接口：

```c
void vision_get_fused_pose(...);
uint8 vision_get_object(uint8 type, uint8 object_id, object_state_t *out);
uint8 vision_get_map_snapshot(map_snapshot_t *out);
uint8 vision_map_changed(void);
void vision_request_full_map(uint8 reason);
```

算法层和中间层不得直接读取UART接收缓冲，也不得依赖协议字段偏移。

---

## 13. 位姿融合

OpenART提供低频绝对位置，IMU和编码器提供高频帧间增量。

首阶段采用简单可运行方案：

1. 收到有效视觉位姿后更新视觉参考点。
2. 原子记录当前里程计累计值作为参考基准。
3. 后续融合位置等于视觉参考位置加基准后的里程计增量。
4. 航向主要使用IMU，视觉角度用于校准和异常检查。
5. 视觉位置明显跳变时不立即覆盖，先标记无效并保留上一参考。
6. 视觉长时间无效时，中间层降速，超过安全时限后停车。

不能在任意中断时刻粗暴清零共享里程计变量。

---

## 14. 算法层输入

算法层只消费已提交的一致快照：

```text
map_snapshot_t {
    map_version
    walls
    goals
    boxes
    bombs
    car_grid
}
```

算法层使用整格状态进行搜索，不直接消费视觉颜色置信度、遮挡模板或连续运动历史。

每次求解结果记录：

```text
source_map_version
```

若执行期间收到更高的 `map_version`，旧Action序列失效，需要重新规划。

## 15. 中间层执行状态机

保留原规划主状态：

```text
IDLE
MOVING
PUSHING
    ├─ APPROACH
    └─ PUSH_EXEC
WAITING
DONE
STUCK
```

### 15.1 PUSH完成判定

不能再使用“对象本帧不存在”等价于完成。

完成条件：

```text
当前对象ID与Action.object_id一致
并且对象状态明确为COMPLETED
或者对象VALID且已稳定到达明确目标格
```

以下状态不能判定完成：

```text
OCCLUDED
LOST
视觉包超时
对象ID不匹配
```

开环推距仅作为视觉短暂延迟时的保护和降速依据，不应直接覆盖明确的视觉冲突。

### 15.2 STUCK与重规划

触发条件包括：

- Action超时。
- 物体长时间无有效位移。
- 视觉对象状态为LOST。
- 当前地图版本发生变化。
- 融合位姿失效。

处理流程：

```text
停止运动
→ 请求FULL_MAP
→ 获取已提交的新快照
→ 主循环调用solve()
→ 原子替换Action队列
→ 恢复执行
```

`solve()`不得放在5ms控制中断中执行。

---

## 16. 控制层

控制层保持原规划：

```c
void motion_set_world_velocity(float vx, float vy, float omega);
```

- 世界坐标速度由中间层计算。
- 控制层负责世界坐标到车体坐标转换。
- 控制层负责运动学、PID和PWM。
- PUSH_EXEC期间继续使用IMU航向保持，防止车体自转影响世界速度方向。
- 车辆朝向不参与游戏推动方向判断。

低频：静态格强证据检查

5ms中断中只执行有界任务：

```

地图快照转换
solve()

大批量调试输出
```

## 18. 分阶段实施

### 阶段0：稳定基线

- 保留当前OpenART稳定版本备份。
- 固定测试图片、地图真值和当前通信输出。
- 后续每阶段均可切回稳定版本。

### 阶段1：OpenART内部三层状态

- 建立静态层、动态层和车辆层数据结构。
- 保留现有识别算法作为正式结果来源。
- 新状态在影子模式运行。
- 新旧合成地图必须一致。
- 不修改UART正式输出。

### 阶段2：首帧初始化与纯合成

- 首帧结果写入独立层。
- 为箱子和炸弹分配稳定ID。
- `FULL_MAP`改为纯合成，不反向修改任何层。
- 验证输出与旧流程一致。

### 阶段3：精简协议联调

- 双端加入协议版本、地图版本和对象状态。
- 动态坐标升级为 `0.1格`。
- 炸弹容量统一为3。
- MCU协议层转换为统一世界状态。
- 保持固定长度和XOR校验。

### 阶段4：打通自动执行闭环

- 算法读取一致地图快照。
- 中间层加载Action。
- 融合位姿驱动MOVING。
- PUSH使用固定对象ID闭环。
- 完成一次完整的识别、规划、移动和推动流程。

至此视为“第一条能跑的线”完成。

### 阶段5：ACTIVE/FROZEN动态跟踪

- 车辆附近局部跟踪。
- 区域外冻结输出。
- 加入单轴运动和禁止连锁推动约束。
- 降低常规帧计算量。

### 阶段6：遮挡处理

- 目标遮挡下保持对象ID。
- 墙体遮挡下保持炸弹状态。
- `OCCLUDED`不能触发错误完成判定。

### 阶段7：爆炸和地图版本

- 实现3×3候选更新。
- 实现5×5高质量验证。
- 原子提交地图并增加版本。
- MCU收到变化通知后请求全图并重规划。

### 阶段8：健壮性增强

- OpenART重启识别。
- CRC16。
- 双向动作上下文提示。
- 更完整的错误码、超时和重发策略。
- 长时间回归和故障注入测试。

## 19. 首条可运行链路验收标准

阶段4完成时至少满足：

1. OpenART能稳定输出正确的初始地图。
2. 箱子和炸弹具有稳定对象ID。
3. 车辆连续坐标和角度能被MCU正确解析。
4. MCU能请求并收到FULL_MAP。
5. 算法能基于该快照生成Action。
6. 中间层能消费融合位姿执行移动。
7. 中间层能按对象ID观察推动结果。
8. `OCCLUDED/LOST`不会被误判为完成。
9. 协议超时或地图变化时车辆能够停车。
10. 控制5ms周期不被识别、规划或调试输出阻塞。

---

## 20. 当前暂不追求的能力

为了优先打通链路，以下内容不作为第一阶段阻塞项：

- 任意设备独立重启后的无缝恢复。
- 所有视觉异常的自动自愈。
- 完整的双向动作提示协议。
- 高可靠通信重传系统。
- 所有遮挡情况一次性解决。
- 多次连续爆炸的极端压力测试。
- 通用化、可扩展到未知对象数量的协议。

这些能力应在主链路稳定后按实际问题逐项增加。

---

## 21. 最终原则

```text
先打通链路，再增加健壮性。
协议传递事实，不传递视觉内部实现细节。
视觉维护世界观测，中间层维护动作执行。
对象不可见不等于对象完成。
对象ID在整个任务周期内保持稳定。
地图只发布已提交版本，不发布候选状态。
算法只消费一致快照，不直接依赖串口格式。
规划和高计算量识别不得阻塞5ms控制周期。
```
