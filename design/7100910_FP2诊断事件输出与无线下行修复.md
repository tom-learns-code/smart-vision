# 7100910 FP2诊断事件输出与无线下行修复

## 现象与结论

实测日志中第二摄像头已经正常在线：`fp_id=7200102`，`SESSION_INIT 3/3`后进入`READY session=1 ready=1`，MCU端`crc=0 fmt=0 drop=0`。因此第二摄像头、UART1 B12/B13、摄像头UART12和FP2初始化协议均已打通。

之后PC发送`1`和`4`时，日志里没有对应的`UART8_RX ... ascii='1'/'4'`，MCU的`tx`仍为1、`state`仍为READY，没有进入REQUEST_WAIT。这证明请求未进入MCU UART8接收，而不是第二摄像头识别或FP2请求失败。

根因是FP2诊断菜单把第二摄像头每2秒一次的端口探测包计数变化也视为状态变化，因而每2秒通过无线UART8发送一条较长的`FP2_STATUS`。UART8代码自身是IRQ发送队列，但无线透明传输链路在持续上行期间反向命令明显延迟或丢失。

## 修改

- MCU版本：`7100910 / FP2_DIAG_EVENT_QUIET`。
- 删除`roi.rx_packets != g_last_roi_packets`这一自动输出触发条件。
- 摄像头仍每2秒发探测包，MCU仍持续解析并用5秒阈值判定在线；保活能力不变。
- FP2状态只在在线状态、会话状态、MCU发送请求、匹配结果等实际事务事件变化时自动打印。
- `S`命令仍强制打印完整FP2统计，可随时人工检查rx/proto/tx/match/timeout/crc/fmt/drop。
- MCU、第二摄像头之间的FP2协议、2秒请求超时、伪识别、求解器、控制层和全局视觉均未修改。

修改前备份：`design/_codex_backups/checkpoint_7100909_before_fp2_diag_quiet_20260719_214525`。

正式构建：ARMClang 6.16，`0 Error(s), 0 Warning(s)`，程序尺寸`Code=215216, RO=25368, RW=680, ZI=631268`。AXF为`project/mdk/Objects/rt1064.axf`，SHA256=`5A9C7C4628D842B93F4958946444BD2BFAE40A450C6838AFBE7662E0A3B4C99F`。

完成态备份：`design/_codex_backups/checkpoint_7100910_fp2_diag_event_quiet_built_20260719_215004`。

## 复测流程

```text
下载7100910 AXF并完全重新上电
-> 确认 #MCU_BOOT id=7100910 stage=FP2_DIAG_EVENT_QUIET
-> F -> I
-> 等待 state=READY ready=1
-> 此后READY状态不应再每2秒刷FP2_STATUS
-> 1
-> 应立即看到UART8_RX ... ascii='1'和REQUEST_WAIT
-> 约1秒后看到FP2_RESULT type=BOX_IMAGE status=OK
-> 4
-> 约1秒后看到FP2_RESULT type=GOAL_DIGIT status=OK
-> S核对tx>=3、match>=2、timeout=0、crc=0、fmt=0、drop=0
```

如果静默后仍看不到`UART8_RX`，则问题已经完全落在PC无线模块下行、模块供电或D17线路，不属于第二摄像头或FP2代码；此时用同一串口连续发送一个普通`H`即可验证UART8下行。
