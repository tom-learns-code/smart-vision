## 3. FP2二进制协议

FP2固定帧长20字节，小端序，异或校验。字段布局：

| 字节 | 含义 |
| --- | --- |
| 0..1 | 帧头`A5 5A` |
| 2 | 协议域`F2` |
| 3 | 版本`01` |
| 4 | 帧类型 |
| 5 | session_id |
| 6 | request_id |
| 7 | object_type：0无、1箱子图片、2目标点数字 |
| 8 | object_slot |
| 9 | arg0：初始化时为箱子数，结果时为识别ID |
| 10 | arg1：初始化时为目标点数，结果时为置信度百分比 |
| 11 | status |
| 12 | 发送序号 |
| 13..16 | sender_build_id，小端 |
| 17..18 | 保留 |
| 19 | 前19字节异或校验 |

帧类型：

- `0x40 SESSION_INIT`：MCU发送箱子数和目标点数。
- `0x41 INIT_ACK`：第二摄像头确认会话。
- `0x42 IMAGE_REQUEST`：请求识别箱子图片。
- `0x43 DIGIT_REQUEST`：请求识别目标点数字。
- `0x44 RESULT`：返回识别ID、置信度和状态。
- `0x45 RESET_SESSION`：清除当前会话和未完成请求。
- `0x46/0x47 PING/PONG`：保留的链路探测。

状态码0..7依次为：OK、LOW_CONFIDENCE、MODEL_MISSING、BAD_SESSION、BAD_SLOT、BUSY、BAD_FRAME、INTERNAL_ERROR。MCU本地另用8表示2秒事务超时。

MCU端使用256字节RX环形缓冲，既保留旧10字节端口探测帧解析，也解析FP2 20字节帧。会话初始化每500ms重试，最多3次；单次识别等待上限2秒。结果必须同时匹配session、request、object_type和slot，旧会话或迟到结果只计入stale，不能进入算法。

## 4. 第二摄像头伪识别与真实识别

文件：`openart/openart_roi_classifier.py`

用户开关：

```python
FAKE_RECOGNITION_ENABLE = True
FAKE_RECOGNITION_DELAY_MS = 1000
```

伪识别开启时：

1. 收到`SESSION_INIT(N,N)`后，分别生成两组互相独立的`0..N-1`随机排列：箱子slot到图片ID、目标slot到数字ID。
2. 图片ID和数字ID属于两个独立集合，不能共用一张映射表。
3. 收到图片或数字请求后非阻塞等待约1秒，再返回该session内对应slot的固定ID。
4. 同一会话内同一slot反复识别得到相同ID；新会话重新随机。
5. 重复request会重发缓存结果，不重新抽签；新会话和RESET都会清理旧pending/result。

伪识别关闭时：

- 图片模型沿用`mobilenet.tflite`和标签文件，按请求惰性加载。
- 数字模型目前故意保留为空占位；未部署模型时返回MODEL_MISSING。
- 后续部署真实模型时，必须把模型类别映射成算法要求的`0..N-1`ID，并保留FP2协议与MCU接口不变。

## 5. MCU任务状态机

主要文件：

- `project/code/roi_camera_link.c/.h`
- `project/code/mission_manager.c/.h`
- `project/code/planner_service.c/.h`
- `project/code/bomb_solver_adapter.c/.h`
- `project/code/solver.h`
- `project/code/action_follower.c/.h`
- `project/code/pc_console.c`

炸弹图会强制使用N2求解模式。第一次求解生成`BOMB_P1`计划，其中保留OBSERVE、WAIT和PHASE_END动作，不再当作不可执行注释跳过。

`3 -> E`武装BOMB_P1计划时：

1. MCU先发送RESET，再发送`SESSION_INIT(box_count, goal_count)`。
2. 电机保持硬停，状态进入`FP_SESSION_WAIT`。
3. 收到有效INIT_ACK后进入`STEP_WAIT`；初始化失败或重试耗尽则进入FAULT。

执行OBSERVE时：

1. 根据地图方向和当前航向，用现有point_test+IMU原地转向目标。
2. 停车并等待动作规定的稳定时间。
3. 箱子请求发IMAGE_REQUEST，目标点请求发DIGIT_REQUEST；BOTH按顺序发送两个请求。
4. 等待匹配结果，记录到box_ids/goal_ids和观察掩码。
5. 识别完成后转回原计划航向，再推进动作游标。
6. 识别超时、低置信度、模型缺失、ID越界、重复ID或旋转失败都会硬停进入FAULT，这是当前明确保留的安全边界。

遇到PHASE_END时：

1. 检查箱子和目标点各已观察N-1个。
2. 对两组ID分别执行N-2缺失ID补全。
3. 调用`planner_service_solve_phase2()`生成`BOMB_P2`。
4. 原子替换当前P1计划，从P2第一个动作继续；不要求PC重新按菜单计算。

P2支持普通箱子和炸弹动作。炸弹被推入墙时，以该墙格为中心清除3x3范围内的墙；其他箱子、目标点等元素不随爆炸删除。任务管理器的本地期望地图同步更新，随后继续沿用逐格执行和地图复核。

## 6. 菜单与验证流程

### 6.1 仅验证第二摄像头双向协议

前提：任务必须处于DISARMED，第二摄像头运行`fp_id=7200102`脚本。

```text
完全重新上电
-> 确认 #MCU_BOOT id=7100909 stage=FP2_N2_RUNTIME
-> F
-> I
-> 等待 FP2_STATUS ... state=READY session=... ready=1 count=3/3
-> 1
-> 等约1秒，检查 FP2_RESULT ... type=BOX_IMAGE slot=0 id=0..2 status=OK
-> 4
-> 等约1秒，检查 FP2_RESULT ... type=GOAL_DIGIT slot=0 id=0..2 status=OK
-> 2、3、5、6可验证其余slot
-> S查看统计
-> R重置会话
-> B返回主菜单
```

同一session内，BOX三个slot应构成`0,1,2`的一种排列，GOAL三个slot也应独立构成`0,1,2`的一种排列。不同组可以偶然相同，但它们是独立生成的。进入F菜单才会向PC持续打印第二摄像头状态；正常比赛菜单保持安静。

### 6.2 炸弹P1/P2首次安全验证

先只用`N`逐步运行，不要第一次就按`A`：

```text
完全重新上电
-> 确认全局视觉VISION CONNECTED、第二摄像头FP2 online=1
-> 1
-> 等待FULL_MAP received和MAP_END，确认bomb>0且box=goal
-> 2
-> D
-> 确认PLAN_SUMMARY valid=1/current=1、PLAN_CHECK ok=1
-> 确认PLAN_PHASE type=BOMB_P1_OBSERVE requires_ids=1
-> B
-> 3
-> E
-> 等待MISSION从FP_SESSION_WAIT进入GRID_STEP_WAIT且fp=READY
-> N
```

每按一次`N`执行一个网格、一个OBSERVE事务或一次P1到P2转换。OBSERVE期间正常输出应按顺序出现`OBS_ROTATE_OUT -> OBS_SETTLE -> OBS_WAIT_RESULT -> OBS_ROTATE_BACK`。到PHASE_END后应看到`PHASE2_SOLVING`并切换成`BOMB_P2_DELIVER`。确认逐步模式稳定后，下一次重新上电按同样流程，在`3 -> E`就绪后用`A`连续运行。
