# FP2 7200117 双模型极简切换诊断

## 已确认事实

- 图片模型1、图片模型2和数字模型分别由 7200112、7200113、7200114 单独持续推理，均稳定在约 3.6 FPS。
- 7200116 完整 FP2 融合诊断能加载图片模型1并完成新帧抓取，但停在第一轮 `image1 phase=INFER_BEGIN`，没有进入模型2。
- 因此当前故障不是模型2切换冲突，也不是模型文件、TF卡、USB、供电或阈值问题。
- 主要怀疑是完整 FP2 脚本常驻对象较多，导致 `tf.classify()` 的原生推理工作区内存不足或碎片化。该类底层失败可能不会抛出可捕获的 Python 异常。
- 7200115/7200116 仅执行 `del net` 和 GC，未调用 `tf.free_from_fb()`；帧缓冲模型不一定因此真正出栈。

## 新诊断

- 文件：`openart/fp2_compact_dual_model_diag.py`
- 识别数：`7200117`
- 不含 FP2 协议、UART、伪识别、文件系统遍历和大状态机，只保留相机初始化、两个图片模型、标签和阶段日志。
- 每轮顺序：模型1加载到 framebuffer -> 抓图 -> 推理 -> `tf.free_from_fb()` -> 模型2执行同样流程。
- 每阶段打印 `gc.mem_free()`，用于观察普通堆是否持续下降。
- 此文件只允许从 IDE 临时运行，不得保存为设备 `main.py`。

## 分支判定

1. 若 7200117 能连续输出至少三轮 `FP_DUAL_CYCLE_END`：底层支持模型切换，7200116 的根因就是完整脚本内存占用/碎片；正式实现需拆成更小模块或常驻精简推理服务，并显式 `tf.free_from_fb()`。
2. 若模型1仍停在 `INFER_BEGIN`：动态加载后立即推理这一生命周期本身不可靠；正式实现应改为启动时固定加载单模型，模型切换通过受控重启/模式启动完成，不能在一次 Python 生命周期内切换。
3. 若模型1成功、模型2加载或推理失败：`tf.free_from_fb()` 或固件 framebuffer 栈不能可靠回收；同样改用单模型常驻加受控重启架构。
