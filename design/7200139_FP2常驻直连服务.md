# FP2 7200139 常驻直连服务

## 为什么换架构

7200136 实测在收到图片请求后立即离线，MCU 后续没有收到 Worker 或监听器探活。此前现场还出现过合法 job 留存但无 trace/last，说明“任务文件、解释器复位、启动分发、Worker、再次复位”的链路本身不稳定。继续修复复位交接的收益低于直接缩短链路。

## 新架构

- 新增 `openart/fp2_direct_service.py`，识别号 `7200139`。
- 单进程常驻 UART12：收到 FP2 请求后直接加载对应模型、识别、回包，再继续监听。
- 不创建 job/state/trace/last，不调用 hard/soft reset，不导入分发器和 Worker。
- 保留会话初始化、slot 校验、图片/数字请求区分、共享紧凑 ID 映射、重复请求结果重发、PING/PONG 和 2 秒探活。
- 图片仍使用两个模型，各采集 3 帧类别概率均值，再按 0.80 阈值融合；数字使用一个模型的 3 帧均值和 0.80 阈值。
- 推理期间 MCU 的同 request 重发会暂存在 UART 缓冲；完成后结果主动发送 4 次，随后重复请求还能直接取最近结果。

## 7200140：固定长度协议帧与异常隔离

- 7200139 实测可以持续探活，但收到 `SESSION_INIT` 后未回 ACK 并退出，尚未触发任何模型。
- 电脑端使用真实20字节FP2初始化帧模拟时逻辑和ACK校验均正确，因此优先处理目标MicroPython的容器兼容差异。
- 所有协议帧改为预分配固定长度 `bytearray` 后逐字节赋值，不再使用动态 `append/extend`。
- 每个完整接收包增加异常隔离；单个命令异常只打印 `FP2_HANDLE_ERROR` 并继续探活，不再终止常驻服务。
- 新识别号 `7200140`，已同步H盘；SHA-256=`5EFED9338E05901154DB6A040698DA5C296C2CDFD6EC30126E7678F1FA70C41C`。
- 下一步只验证 `F -> R -> I` 是否进入READY，不触发模型。

## 数字3原始类别诊断结论

- 独立数字基线`7200114 / DIGIT_BASELINE`对准真实数字3连续采样约140帧，模型绝大多数输出原始`index=8`，少量输出`index=7`，没有一次输出`index=3`。
- 多次`index=8`置信度达到0.80至0.98，足以解释正式FP2三帧平均后稳定得到另一紧凑ID且置信度93%至99%；共享紧凑映射没有故障。
- `digit_labels.txt`顺序是标准0至9，本机未找到证明训练输出采用其他排列的训练配置。当前首要判断为数字模型/当前ROI对数字3与8发生高置信度混淆，而不是MCU、协议或阈值问题。
- 不允许把raw8直接硬映射成数字3，因为真实数字8会发生冲突。下一步只需对准真实数字8运行同一基线：若稳定输出3，说明3/8标签可能互换；若仍输出8，说明模型或ROI无法区分3与8，需要调整数据/ROI或重训。
